# scripts/pnr/ — 配置配線

`TR-1um_SCLK_SPI/scripts/`（さらにその元は `TR-1um_Async_I2C/script/`）の
フローを TD4 に移したもの。**アルゴリズムは触らない**方針も同じで、
設計固有の値は `td4_config.py` 1 本に集めてある。

## 動かす場所

`gdstk` と `klayout` の Python バインディングが要る。
**Mac には両方とも入っていない**ので、配置配線そのものはクラウド側で回し、
成果物の GDS を Mac に置いて KLayout GUI で見る、という分担になる。
Mac で動くのは GDS を読まないもの（`td4_config.py` の整合チェックなど）だけ。

| | Mac | device_bash の Linux VM | クラウド |
|---|---|---|---|
| `gdstk` | ✗ | ✗ | ✓ |
| `klayout` (python) | ✗（GUI はある） | ✗ | ✓ |
| `ngspice` / `yosys` | ✓ | ✗ | ✓ |

## STEP と成果物

**STEP ごとに GDS を残す。** 途中で何が起きたかを GDS で追えるようにするため。

| STEP | 内容 | 成果物 |

| step2 | 行内順序（バリセンタ反復） | `layout/step2/place_step2_ordered.gds` |
| step3 | TAP 挿入 | `layout/step3/place_step3_tap.gds` |
| step4 | FILL 挿入（配置の最終） | `layout/step4/place_step4_fill.gds` |
| step5 | 配置 JSON 変換 + 配置 GDS | `layout/step5/route_step_1_placement.gds` |
| step6 | チャネル配線 | `layout/step6/route_step_2_*.gds` |
| step7 | 短絡のリップアップ/再配線 | `layout/step7/route_step_3_ripup_reroute.gds` |
| step8 | トップピンのコア端引き出し | `layout/step8/route_step_4_top_pins.gds` |


## 移植でルータに入れた変更（9 箇所）

原本（`TR-1um_SCLK_SPI` 経由で `TR-1um_Async_I2C`）は**アルゴリズムを触らない**
方針。入れた変更は全部「TD4 移植 (n)」のコメント付き。

| # | 場所 | 内容 |
|---|---|---|
| 1 | `route_channels_nrow_fm.py` | 行幅の直書きを `cfg.ROW_WIDTH_UM` に |
| 2 | 同上 | 行の右端の照合からハードマクロを除く |
| 3 | 同上 | **片側にしかピンが無いマクロのネットを ch[0] に固定**。既定の分類は「ピンのある行」しか見ないので、マクロと row1 を繋ぐネットが ch[1] へ割り振られて詰まる |
| 4 | 同上 | 優先コリドーのセル種を `FILL2` 限定から `FILL*` に |
| 5 | `highlight_top_pins_nrow_fm.py` | `assign out_port = \u_core.reg_out ;` の**エスケープ識別子**を別名として拾う。拾えないと step8 が out_port[0..3] と cflag_o を見失う |
| 6 | `squeeze_channels_nrow_fm.py` | ハードマクロの y 範囲を identity 写像で保護 |
| 6b | 同上 | **保護区間を 2 トラックぶん膨らませる**。保護区間の外側は詰まるので、隣のトラックが区間の脇まで寄って M1 間隔違反が出る（実測 11 件） |

| 9 | `verify_port_connectivity.py` | ハードマクロの帯を「セル行」と数えない |

## メモリを横倒しにした経緯（重要）

縦置き（`REG8x16` をそのまま行の横に）では短絡が 31 件から下がらなかった。
原因は**行の配置率 79%** で、行またぎに使える「M2 の無い x」が 1 行 216 トラック
中 48 本しか無く、158 回の行またぎのうち 63 回が clear な x を見つけられずに
遠くへ逃げていた。

さらに**縦置きはチャネルの圧縮も止めていた**。マクロが 933 µm の剛体で
y 200…1133 を塞ぐため、step10 が削れたのは 507.6 µm のうち 249.8 µm だけ。
実使用 891 µm に対して 1398.6 µm を背負ったままだった。
（KLayout で見ると ch1/ch2 が明らかに空いている、というのがこの症状。）

`scripts/pnr/mkmemport.py` で **R90 + M1/M2 の直交変換**を行い、
上辺にパッド列を持つ `MEMPORT` にまとめた。

| | 縦置き | 横倒し (`MEMPORT`) |
|---|---|---|
| 行幅 | 1177.2 | **1598.4** |
| 行数 | 5 | 4 |
| 配置率 | 79% | **70〜74%** |
| 行またぎの clear x 失敗 | 63 | **4** |
| step10 の圧縮 | 249.8 µm | **1790.1 µm (-62%)** |
| 短絡 | 31 | **16**（→ 下記で **2**） |
| チップ側コア高 | 1457.2 | 1659.1（帯 561.6 込み） |

## マクロのネットが M2 を食う問題（`PER_ROW_LOCAL_NETS`）

KLayout で見ると、`REG8x16` の `Q` が**チャネルで 4 本に分岐して縦コリドーを
走っている**（ユーザ指摘）。実測すると縦 M2 セグメントは

| | 1 ネットあたり |
|---|---|
| マクロにつながる 21 本 | **15.2 本** |
| その他 | 5.2 本 |

`rom_data[4]` は 41 本・15 列を使い、うち 623.7…683.1 は **5.4 µm 刻みの
10 列連続**だった。階段状に x をずらしながら行を登っている。

原因は構造的なもの。マクロのパッドは帯の上辺（= ch[0] の下）にしか無いので
spine は ch[0] 固定で、row1…row3 のシンクへ登るたびに `draw_jog` が新しい
トラックを取る。

`PER_ROW_LOCAL_NETS` に入れると行ごとに専用の guarded トラックを持つので
階段にならない。ただし専用トラックはチャネルを太らせるので入れすぎは逆効果:

| per-row-local に入れる本数 | 行またぎジョグ | 短絡 | 圧縮後コア高 |
|---|---:|---:|---:|
| `clk_buf`/`rst_n_buf` のみ（2 本） | 134 | 20 | 1097.5 µm |
| **+ マクロ 8 本**（`rom_data[4..7]` `d_buf[0..3]`） | **79** | **16** | **1131.1 µm** |
| + マクロ 21 本（全部） | 62 | 22 | 1218.7 µm |

採用は真ん中。`rom_data[4]` の縦 M2 は 41 → 20 本になった。

### 同じ行を何度も跨ぐ問題（手選び → 自動判定）

上の「マクロ 8 本」を手で入れた状態でもまだ妙な分岐が残っていた（ユーザ指摘、
選択されたのは `box(406000,39800 409400,161300) on M2`）。追うと
`\u_core.pc [1]` が

* 縦 M2 5 列（x = 395.2 / 406.0 / 416.8 / 427.6 / 438.4、10.8 µm 間隔）
* ch[1] に平行トランク 5 本（y = 373.0 / 378.4 / 383.8 / 389.2 / 394.6、x 範囲は大半が重複）

を持っていた。**5 本とも同じ row0 を跨いで同じ行へ降りている。**

原因は spanning ネットの扱いそのもの。spanning は「**ピン 1 本ごと**に行を
跨ぎ、そのたび `draw_jog` が新しいトラックを取る」ので、同じ行に複数のピンが
あるネットは同じ行を何度も跨ぐ。設計全体での実測:

| | 行またぎ | うち重複 |
|---|---:|---:|
| 手選び 10 本のとき | 113 本 | **45 本 (40%)** |
| 自動判定（下記）後 | 66 本 | 7 本 (11%) |

per-row-local は行ごとに専用トラックを **1 本**持つので、同じ行を何度跨いでも
増えない。そこで手選びをやめ、**配置 JSON からピン数と行数を数えて自動で決める**:

```python
PRL_MIN_PINS = int(os.environ.get("TD4_PRL_MIN_PINS", "5"))
PER_ROW_LOCAL_NETS = {"clk_buf", "rst_n_buf"} | {
    n for n in npin if npin[n] >= PRL_MIN_PINS and len(nrow[n]) >= 2}
```

しきい値の掃引（step6 時点）:

| `TD4_PRL_MIN_PINS` | per-row-local 本数 | 行またぎジョグ | 短絡 |
|---:|---:|---:|---:|
| 5（既定） | 19 | **28** | **2** |
| 4 | 26 | 23 | 3 |

しきい値を下げると専用トラックが増えてチャネルが太り、かえって悪化する。
step10 まで通した結果: 圧縮 2887.6 → **1127.0 µm (-61.0%)**、M1/M2 の
width/space 違反 0、短絡 **2 件**（どちらもマクロの `ADD` ピン)。
残り 2 件は次節で潰した。

## 残り 2 件の短絡と最後の DRC 1 件（移植 10〜13）

### (10) spanning のレーンを詰めない — `_004_` ↔ `rom_data[5]`

`assign_lanes` は x 区間が重ならないネットを同じレーン（= 同じトラック）に
詰める。ところが spanning のトランクは

```python
xmin, xmax = min(pin_cxs), max(pin_cxs)     # ← ジョグ**後**のピン x
```

で描かれるのに、レーン割り当ては**ジョグ前**の区間で決まる。行またぎで
clear な x を探した結果ピンが右へ動くと、トランクが割り当て時の区間を
飛び出して同じレーンの隣人を踏む。実測:

| ネット | 割り当て時の区間 | lane | 実際のトランク |
|---|---|---:|---|
| `_004_` | (199.8, 1120.5) | 5 | **194.4 … 1541.7** |
| `rom_data[5]` | (1158.3, 1260.9) | **5** | 1158.3 … 1260.9 |

ch0 の y=45.2 で x 1158.3…1260.9 が重なって短絡。spanning は ch0 に 20 本
しか無く、詰めても 11 レーン・詰めなくても 20 レーン（+9 トラック =
48.6 µm）で、**使われないトラックは step10 の圧縮が丸ごと削る**。詰めるのを
やめた（`TD4_SPAN_LANE_PACK=1` で従来に戻せる）。

### (12) 途中の行でも「次のレグ」を見る — `_003_` ↔ `_002_`

v30 は**最後に跨ぐ行**だけ「この先の走行も clear か」を条件に入れていた。
途中の行では次のレグを見ないので、行を跨いだ先のチャネルが他ネットの柱で
埋まっている x を平気で選ぶ。そこから先は x を変えるしか逃げ道が無く、
`draw_jog` は「departure leg が clear なトラックが無い」と言って**無検査
フォールバック**に落ちる。

実測: `_003_` (`u_mem.ADD[2]`) は row1 を x=650.7 で降りたが、`_002_` が
ch1 の x 649.0…652.4 を y 29.0…1255.4 まで既に占有していた。ch1 に入る
y=1259.4 はチャネルの**最上段**なので下へはどこへも行けず、フォールバックが
y 1259.4→1233.8 の柱を無検査で描いて **21.6 µm** 重なった。

途中の行でも「この行の向こう側の境界 → 次に跨ぐ行の手前の境界」を条件に
加えた。これで `_003_` は最初から別の x を選ぶ。

### (11) ブリッジを cur_y 以外の y でも試す

v28 のブリッジ（トラックを取らずに M1 だけで clear_x へ渡る最後の手段）は
`cur_y` でしか試さない。cur_y…near_y のトラック grid を近い順に試すように
した。上の (12) で `_003_` は救われたので今回は発火していないが、同じ
行き詰まりの受け皿として残してある。

### (13) 同じネットでも via のカット間隔は見る

`collides` の `exclude_net` は「同じネットなら 1 本の導体だから無視」という
趣旨だが、**DRC のカット間隔だけは導体が同じでも効く**。カット 1.4 µm・
最小間隔 1.5 µm なので中心間 2.9 µm 以上要る。

実測: `rom_data[3]` のマクロ側ライザ着地 x=21.6 と `_166_.A` のピン x=24.3 が
同じトランク (y=18.2) に **2.7 µm 間隔**で並び、V1 space 1.3 µm の違反 1 件に
なっていた（唯一の残存 DRC）。同じトラック上に限り同ネットでも 2.9 µm を
要求するようにした。

### (14) 圧縮の Y マップが y<0 を 1750 µm 下へ飛ばしていた

ユーザが KLayout で「帯とコアの間に長い縦 M2 だけの空白がある」と指摘。
実測すると `MEMPORT` は **step9 で -567.9…-10.8、step10 で -2317.7…-1760.6**。
圧縮量 1749.8 µm ぶん**下へ**動いていた。

`build_y_map` のブレークポイントは `(0,0)` から始まり、`y_map` は下限の
ケースを持っていなかったので、y<0 が最後の

```python
return y + (ny_last - oy_last)        # = y - 1749.8
```

に落ちていた。移植元にはルータ座標の y<0 に置くものが無かったので露出して
いなかった。**最初のブレークポイントより下は恒等**に直した。

これだけでチップ側コア高が **3455.5 → 1721.9 µm**。

### (16) M1 電源バスバーの場所を確保（ユーザ指示）

帯の上辺と ch[0] の間は M2 のライザが縦に抜けるだけで **M1 が 1 本も無い**。
横向きの M1 バーを通すのに都合がよいので、ここに VDD/VSS のバスバー
（M1・幅 10 µm）2 本ぶんの場所を空けた。

```
MACRO_GAP_UM = 10.8 → 27.0     # 1.4 + 10 + 1.4 + 10 + 1.4 = 24.2 → grid 27.0
POWER_BAR_W = 10.0 / POWER_BAR_GAP = 2.0
power_bars() → [("GND", -25.0, -15.0), ("VDD", -13.0, -3.0)]
```

`td4_config.check()` が「バーが隙間に収まるか」「上端が ch[0] に近すぎないか」
「隙間がサイトグリッドに乗っているか」を import のたびに見る。
枠は **(250,1)**、ラベルは (250,2) に出してある（チャネル注釈は (250,0)）。
ルータはここに何も描かない。実配線はチップ組み立てで TAP の M2 柱と
マクロ右端の電源に繋ぐ。

### (17) ルータが非決定的だった

`MACRO_GAP_UM` を変えたら短絡 0 → 4 に増えた。調べると **同じ配置 JSON
（md5 31d6cb77…）から走らせても step6 が 3 短絡 → 0 短絡と揺れる**。
ルータのどこかで集合を反復していて、`PYTHONHASHSEED` で順序が変わる。
`route.py` / `place.py` の `__main__` で `PYTHONHASHSEED=0` を立てて
`os.execv` で起動し直すようにした（3 回連続で同一結果を確認）。

**`sweep_seed.py` も直した。** 短絡 0 のとき `PROBLEM(S) FOUND` が出ないのを
「配線が落ちた」と誤判定して、**一番良いシードを捨てていた**
（seed 1 と 9 が 0 件なのに `---` 表示で、seed 8 の 1 件を「最良」と報告）。

なお `lef/TR-1um_PNR.lef` をパッド重心順に作り直した時点で配置もやり直す
必要があった（`macro_pin_x` が LEF のピン矩形を読む）。**seed 1** で 0 短絡。

## コア高を詰める（移植 18〜20）

`layout/step10/route_step_6_squeezed.gds` の実 BBOX 1721.9 µm の内訳:

| | µm | 割合 |
|---|---:|---:|

### 効かなかったもの（実測）

`scripts/pnr/sweep_height.py` で振った。行数・PRL しきい値・トラック
ピッチは**どれも詰められない**。

| 振ったもの | 高さ | 短絡 | DRC | 判定 |
|---|---:|---:|---:|---|
| 4 行（現行） | 1721.9 | 0 | 0 | — |
| 5 行（seed 1/2/3） | 1931.8〜1984.5 | 2〜16 | 0 | **行を増やすとチャネルが 1 本増えて +210 µm** |
| 6 行 | 2136.2 | 2 | 0 | +414 µm |
| 3 行 | — | — | — | セルが入りきらない（`_233_`） |
| `PRL_MIN_PINS` 6（seed 1〜4） | 1603.1〜1689.5 | 3〜11 | 0 | 短絡 0 にならない |
| `PRL_MIN_PINS` 7 | 1640.9 | 8 | 5 | 同上 |
| トラックピッチ 5.0 | 1593.6 | 0 | **13** | 下記 |

**トラックピッチ 5.4 はすでに下限**。`via_1` は M1 と M2 の**両方**に 3.4 角の
パッドを置くので、隣接トラックの via が同じ x に来たときの拘束は

```
M1: 3.4 + 1.4 (M1 最小間隔) = 4.8
M2: 3.4 + 2.0 (M2 最小間隔) = 5.4   ← こちらが効く
```

実測でも 5.0 にすると M2 の間隔違反がちょうど `dy=1.6 dx=3.4`（= 5.0 − 3.4）
で出た。`route_channels_nrow_fm.py` が下限を検査して落ちるようにしてある。

### (20) `MEMPORT` の M1 段を右半分ぶん減らす — **−48.6 µm**

マクロの**上**に M1 の段を取るのは「マクロの OBS を越えて x<933 のパッドへ
行く」ためだけ。ライザ列（x 943.7…1078.1）より**右**のパッドへは、マクロの
右の空き地（x 933…1598.4、y 0…399.6）を**ピン自身の y のまま**水平に走れる。

段が 25 本 → **16 本**、帯が 550.8 → **502.2 µm**。

**パッドの割り当てを変えずに**入れるのが肝。`--pads-from-lef` で既存 LEF の
「パッド x ↔ ネット」をそのまま引き継ぐと、配置器が見るマクロのピン座標
（x = パッド x、y = −`MACRO_GAP_UM` − 5.7 = −36.1）が **1 µm も動かない**ので、
配置も配線もビット単位で同じものが出て、帯の**下**だけが縮む。

```sh
python3 scripts/pnr/mkmemport.py --pads-from-lef lef/TR-1um_PNR.lef
```

`--order-from`（負荷の重心順に並べ替え）を使うと逆に配置がやり直しになり、
配線がサイコロの振り直しになる。実測: 20 シード振って短絡 0 は 1 つも出ず、
最良で 1 件だった。**帯の高さだけ変えたいときは `--pads-from-lef`。**

## 縦置き再訪（`TD4_MACRO_MODE=portrait`）

ルータを一通り直したので、最初に諦めた**縦置き（`REG8x16` を回さず行スタックの
右に置く）+ 5 行**をもう一度測った。`td4_config.py` にモードを残してある。

| 行 | 4 行 × 1598.4 | 5 行 × **1177.2** |
| 充填率 | 70〜74% | **78〜82%** |
| 帯 / 隙間 | 502.2 + 27.0 | **無し** |
| **コア高（実 BBOX）** | **1645.0**（コリドー FILL3 化後） | **1331.2〜1403.7** |
| 行またぎで clear な x が見つからない | **0 回** | **26〜33 回** |

| DRC | 0 | 0 |

**高さは 250〜290 µm 縮むが、短絡が 0 にならない。** 原因は 3 年前と同じで
**行の充填率**。行幅が 1598.4 → 1177.2 に縮むぶんセルが詰まり、行を跨ぐときの

出ない**のに対し、縦置きでは 26〜33 回出て、そのたび無検査のフォールバックに
落ちる。ルータ側の修正（移植 10〜13）は短絡を 31 → 3 まで減らしたが、
**空き列そのものが無い**のはルータでは埋められない。

### 縦置きの高さの決まり方（実測で分かったこと）

マクロは参照なので **step10 の圧縮がその y 範囲（933 µm）を貫通できない**。
つまり

```
コア高 = ch[0] の圧縮後 + 933（マクロの span） + マクロより上の圧縮後
```

`ch[0]` はマクロの下なので圧縮が効く（マクロの 21 本が全部ここを通るので
37〜39 トラック ≒ 200 µm 要る）。**マクロの 933 µm の中に入る行とチャネルは
タダ**なので、`CH_HEIGHTS` はそこに row0〜row3 が収まるよう**絞る**のが正解:

| `CH_HEIGHTS` | 933 の中に入る行 | 高さ |
|---|---|---:|
| `240,230,230,230,210,70` | row0…row3 | **1403.7** |
| `240,250,250,250,400,250` | row0…row2 | 1463.7 |
| `200,200,200,200,400,250` | — | ルータが落ちる（ch1 が足りない） |

row4 まで入れるには ch1…ch4 を 174 µm（32 トラック）にする必要があるが、
実測の必要量が 35〜42 トラックなので**不可能**。1400 µm 前後が縦置きの底。

6 行も試したが、チャネルが 1 本増えるぶん「マクロより上」が厚くなって
1678 µm 相当の見込みになり、意味が無い。

### 副産物: `PER_ROW_LOCAL_NETS` が 1 つ前の配置を見ていた

縦置きを試した直後に横倒しへ戻したら、**配置は同じ (md5 e371a97d) なのに
短絡が 0 → 3** になった。`route.py` の

```python
PER_ROW_LOCAL_NETS = {"clk_buf", "rst_n_buf"} | _prl_nets()   # ← import 時に確定
```

が読む `cfg.PLACEMENT_JSON` は **stage5 が作り直す**ので、import の時点では
1 つ前の実行のもの（縦置き 5 行）が残っていた。結果 per-row-local が
19 → 24 本になっていた。`per_row_local_nets()` を関数にして stage6 の中で
呼ぶようにした。`route.py` の行数アサートと同じ罠（移植 14 と同類）。

### 優先コリドーを増やす案を試した（移植 22）

「行のフィラーを全行同じ x に揃えて縦に抜ける列を作る」案（ユーザ提案）。
`PRI_CELL` / `PRI_PITCH` を環境変数にして振った（`TD4_PRI_CELL` /
`TD4_PRI_PITCH`）。`scripts/pnr/plot_corridors.py` で目視できる。

**縦置き（seed 11、`240,230,230,230,210,70`）:**

| コリドー | 本数 | clear-x 失敗 | 短絡 | 高さ |
|---|---:|---:|---:|---:|
| `FILL2` / TAP 直後のみ | 12 track | 43 | 6 | 1387.5 |
| `FILL2` / pitch 216 | 18 | 50 | 6 | 1403.7 |
| `FILL2` / pitch 162 | 24 | 55 | 9 | 1376.7 |
| **`FILL3` / TAP 直後のみ** | **18** | **38** | **4** | 1387.5 |
| `FILL3` / pitch 216 | 27 | 46 | 9 | 1387.5 |
| `FILL3` / pitch 162 以下 | — | — | — | **配置が入らない** |

**増やすほど悪化する。** 理由は 2 つ:

1. コリドーは**予約**なので、増やすほど行の実効幅が減る。縦置きは
   充填率 81% なので、pitch 81 では `4303.8 µm 必要、4212.0 µm しかない`
   と配置が物理的に不可能になる。
2. コリドーに使ったぶん**普通の FILL が減る**。普通の FILL は行ごとにばらばらな
   x にあるが、それでも「たまたま空いている列」を供給していた。それを
   全行共通の少数の x に集約すると、**同じ x に行またぎが殺到して互いに
   衝突する**（`no clear X found` がむしろ増えるのはこれ）。

**効いたのは幅のほう。** `FILL2` (10.8 = 2 トラック) は上側トラックの via パッド
（半幅 1.7 + 隙間 2.0）が隣のセルへ 1.0 µm はみ出すので、隣に M2 があると実質
1 本しか使えない。`FILL3` (16.2 = 3 トラック) なら**真ん中の 1 本が必ず両側とも
空く**。本数を変えずに幅だけ広げると縦置きで 6 → 4 短絡、横倒しでも効いた:

| 横倒し・seed 1 | 高さ | 短絡 | DRC | 行またぎジョグ | コリドー |
|---|---:|---:|---:|---:|---:|
| `FILL2` | 1655.8 | 0 | 0 | 28 | 12 track |
| **`FILL3`（既定に）** | **1645.0** | **0** | **0** | **26** | 18 track |

**`PRI_CELL` の既定を `FILL3` にした。** −10.8 µm。

ついでに配置器を 2 つ直した（コリドーを増やすと露出する）:

* `pad()` が `FILL1` (5.4) も使えるようにした（`TD4_USE_FILL1=1`。既定は
  従来どおり `FILL3`/`FILL2` だけ — 入れると隙間の刻みが変わって配置が
  丸ごと変わるため）
* `pack_row()` に**取りこぼしの回収**を足した。区画への割り当ては「左から
  1 回だけ見る貪欲」なので、区画が細かいと最後に数個あぶれて step3 が落ちる
  （実測: 縦置き・pitch 108 で 2 個）。容量の残っている区画へ best-fit で
  入れ直す。詰め方の性格（quota で均等に散らす）は変えていない。

### 5 行を詰め切れるか（ユーザ再依頼ぶんの追試）

「`REG8x16` を縦置きで右または左に寄せ、残りを 5 段の標準セルで」を条件に、
コリドーを `FILL3` にしたうえで振り直した。

| 設定 | 高さ | 短絡 | clear-x 失敗 | 備考 |
|---|---:|---:|---:|---|
| `240,230,230,230,210,70` seed 1 | **1403.7** | **4** | 24 | 最良 |
| 同 seed 11 | 1387.5 | 4 | 38 | |
| 同 seed 9 | 1387.5 | 13 | 23 | |
| 同 seed 2/3/5 | — | — | — | ch1/ch2 のトラックが足りず落ちる |
| `240,260,260,260,210,70` seed 1〜11 | 1452〜1492 | 4〜12 | 23〜38 | **チャネルを広げても短絡は減らない** |
| 6 行 `240,230×5,70` | — | — | — | ch2/ch3 が足りず落ちる（300 µm 必要 → 高さ約 1725） |

**チャネルを広げても短絡が減らない**のが決定的だった。詰まっているのは
チャネルのトラックではなく**行を跨ぐときの空き列**で、`no clear X found` の
内訳は row0 が 10 回・row1 が 7 回・row2 が 7 回。row0 が最も多いのは、
**マクロの 21 本が幅 400 µm の帯から一斉に ch[0] へ入り、そこから row0 を
越えて上へ抜ける**ため。横倒しの `MEMPORT` はパッドをコア幅いっぱいに散らして
まさにこれを避けている。

成果物は `layout/portrait/` に置いた（**短絡 4 件が残っているので流用不可**、
目視用）:

```
layout/portrait/portrait_5row_step10.gds        1604.7 x 1403.7 um
layout/portrait/portrait_5row_step4_place.gds   配置だけ
layout/portrait/portrait_5row.png
```

### 右サイド / 左サイドについて

**どちらでも配線結果は同じ。** マクロを左に置くのは、行スタックを右へ
421.2 µm ずらすのと同じで、コア全体を **Y 軸ミラー**したものに等しい。
ルータは x 方向に対称な扱いをするので、鏡像は短絡数もトラック数も変わらない。
チップ組み立てでコアを `MX` で置けば、同じ GDS のままマクロが左に来る。
（そのため `td4_config.py` には side のスイッチを作っていない。）

### コア右に D/Q 専用の縦 M2 バスを立てる案（ユーザ提案）の検討

**結論: 16 本は要らない。7〜8 列で足り、幅の予算的にもそこが限界。**

行スタックとマクロの間の帯（いま 21.6 µm = 4 トラック）は**セルが 1 つも
無い**ので、ここを縦に走る M2 は**行を 1 つも跨がない**。マクロのネットを
ここへ逃がせれば `no clear X found` を根本から消せる、というのが提案の核心。
正しい。問題は**何本要るか**と**幅がどこから出るか**。

#### 何本要るか（実測、縦置き row1・seed 1 の配置）

マクロの 21 本が実際にまたがるチャネルの範囲を数えた:

| チャネル span | 本数 | y 区間パッキング後 | ネット |
|---|---:|---:|---|
| ≥ 2 | 13 | **13 列** | `ADD[3]` `D[3..6]` `Q[0..7]` |
| ≥ 3 | 7 | **7 列** | `ADD[3]` `Q[0]` `Q[2]` `Q[3]` `Q[4]` `Q[6]` `Q[7]` |
| ≥ 4 | 1 | 1 列 | `Q[3]` |

* **`D[*]` と `nib_lo[*]` は ch[0…2] に収まる**（負荷が row0/row1 に固まる）。
  遠くまで行くのは **`Q[*]`（`rom_data`）だけ**。
* **y 区間パッキングは効かない**（13 本 → 13 列）。全部がマクロの出口
  ch[1] から始まるので区間が必ず重なる。つまり**バスの幅 = 本数**。

いま残っている 6 件の `clear-x` 失敗も `rom_data[1] [2] [3]` と
`ld_addr[2]` `_089_` で、**Q 系が主犯**。狙いは合っている。

#### 幅がどこから出るか

コア幅は 1600 を超えるとフレーム開口が 1840 → 1600 に落ちるので 1598.4 固定。
マクロ 399.6 も固定。つまり**バスの幅はそのまま行幅から引かれる**:

| バス列 | 帯幅 | 行幅 | 充填率（コリドー 6 本） | 充填率（3 本） |
|---:|---:|---:|---:|---:|
| 0（現状） | 21.6 | 1177.2 | 83.0% | 79.3% |
| 4 | 43.2 | 1155.6 | 84.8% | 80.9% |
| **8** | **64.8** | **1134.0** | 86.6% | **82.6%** |
| 13 | 91.8 | 1107.0 | 89.1% | 84.8% |
| **16** | **108.0** | **1090.8** | **90.6%** | 86.2% |

**16 列は不可能。** 充填率 90.6% では配置が組めない（実測で 88% 台から
`行に入りきらない` で落ちる）。コリドーを 3 本に削って 86.2% にしても厳しい。

**8 列 + コリドー 3 本なら 82.6%** で、いまの 83.0% とほぼ同じ。
バスに逃がす 8 本ぶんの行またぎが丸ごと消えるので、差し引きで勝てる見込み。

#### 実装の見通し

既存の `PER_ROW_LOCAL_NETS` が「行ごとのトランク + それを繋ぐ spine」を
すでに作っている。**バスはその spine を行の中ではなく帯に移すだけ**:

| 場所 | 変更 |
|---|---|
| `td4_config` | `SIDE_BUS_TRACKS`、`MACRO_SIDE_GAP = 21.6 + n*5.4`、`ROW_WIDTH_UM` を引く |
| `route_channels_nrow_fm.py` pass 0 の spine | バス対象ネットは `find_row_clear_x` を呼ばず、**予約した帯の x を そのまま使う**（帯にはセルが無いので無条件に clear） |
| 同上 | バス x の割り当て（ネット → 列）。区間パッキングは効かないので素直に 1 本 1 列 |

`in_bounds`（行またぎ x の上限 = `ROW_WIDTH_UM`）はそのままでよい。
バスは行を跨がないので `find_row_clear_x` を通らない。

**推奨: `Q[0..7]` の 8 本だけをバスに載せ、優先コリドーを 3 本に減らす。**

#### 実装して測った（移植 24、`TD4_SIDE_BUS` / `TD4_SIDE_BUS_PINS`）

| 場所 | 変更 |
|---|---|
| `td4_config` | `SIDE_BUS_TRACKS`、`MACRO_SIDE_GAP = 21.6 + n×5.4`、`ROW_WIDTH_UM` を引く、`side_bus_x()`、`check()` で帯に収まるか検査 |
| `route_channels_nrow_fm.py` pass 0 の spine | バス対象は `find_row_clear_x` を呼ばず予約した x をそのまま使う（`row_signal_used` にも入れない） |
| `route.py` | `side_bus_nets()`（マクロのピン名の接頭辞で選ぶ）。バス対象は必ず per-row-local にする |
| `plot_corridors.py` | バスの帯を水色で重ねる |

結果（縦置き 5 行・`TD4_MACRO_ROW=1`・seed 1・`CH=250,450,230,190,190,85.4`）:

| | バス無し | バス 8 本（`Q[*]`） | **バス 9 本（`Q[*]` + `ADD[3]`）** |
|---|---:|---:|---:|
| 行幅 | 1177.2 | 1134.0 | **1128.6** |
| 高さ | 1331.2 | 1347.4 | **1347.4 µm** |
| **`no clear X found`** | **6** | **1** | **0** |
| 短絡 | 6 | 4 | **4** |
| DRC | 0 | 0 | **0** |

**行またぎの失敗がゼロになった。** 最初の縦置き（row0 合わせ・バス無し）が
24 件だったので、`TD4_MACRO_ROW=1` で 6 件まで、縦バスで **0 件**まで落ちた。
`rom_data[*]` は警告にも短絡にも**一度も出てこなくなった**。

9 本目に `ADD[3]` を足したのは、これが `Q[*]` 以外で唯一チャネル span が
3 以上あるネットだったから（上表）。これで残り 1 件も消えた。

残る短絡 4 件は `rst_n_buf` `wr_hi` `\u_core.reg_out [0]` `ld_addr[2]` で、
**マクロとは無関係の普通の混雑**。行の充填率が 87% あるのが効いている。

他のシードは ch[2]/ch[3] のトラックが足りず落ちるか、短絡 9〜13 件。
seed 1 が突出している。

#### 帯の余りを 3 トラック行へ返した（ユーザ指摘）

KLayout で見ると**バスの右端とマクロの間に 19.9 µm 空いていた**。
`MACRO_SIDE_GAP` の余りを 21.6 → **5.4** に詰めて、浮いた 16.2 µm
（3 トラック）を行幅へ返した。

必要なクリアランスを実測し直して決めた。拘束は M2 同士ではなく
**via の M1 パッド**（半幅 1.7 + M1 最小間隔 1.4 = **3.1 µm**）で、
`REG8x16` の左端は M1 が prBoundary そのもの（実測 M1 0.00 / M2 1.00 /
V1 2.00 / GC 2.50）。余り 5.4 なら行側 5.4 / マクロ側 5.4 で両側とも足りる。

| | 前 | **後** |
|---|---:|---:|
| 行幅 | 1128.6 | **1144.8**（+16.2 = 3 トラック） |
| 帯 | 70.2 | 54.0 |
| 充填率 | 87.1% | **85.7%** |
| 短絡 | 4 | **3** |
| `no clear X found` | 0 | **0** |
| 高さ | 1347.4 | 1347.4 µm |

`TD4_PRI_MODE` も足してコリドーを 3 本（9 track）に減らす案も試したが、
**結果は 1 ビットも変わらなかった**（短絡 3 / 高さ 1347.4 / keep も同じ）。
`partition` の上限が「平均 × (1+tol)」で決まっていて、行の実効幅が
増えてもセルの行割当が動かないため。

残る 3 件は `wr_hi` `\u_core.reg_out [0]` `ld_addr[2]` で、どれも
マクロとは無関係。`ld_addr[2]` の 1 件だけ `draw_jog` の警告が出ている
（ch[2]、x=137.7）。

### 判断

**横倒しのまま（既定）。** 縦置きは 250 µm 安いが短絡が残り、その原因が
配置の充填率なので、いまの行幅ではどうにもならない。縦置きを本気で使うなら

* コア幅を 1600 超に広げる → **フレーム開口が 1840 → 1600 に落ちる**ので不可
* セルを減らす（合成をやり直す）
* 行のフィラーを全行同じ x に揃えて縦に抜ける列を作る（優先コリドーの拡張）

のどれかが要る。モードと測定値は再現できるよう残した。

### マクロの底面を row1 に合わせる（移植 23、`TD4_MACRO_ROW`）

マクロの信号ピンは下辺 1 列なので、**底面を合わせた行 k の下の ch[k]** が
出口になる。k=0 だと 21 本全部が row0 を越えて上へ抜ける。k=1 にすれば
row0 へは下り・row1…row4 へは上り、と分かれる。

直した箇所は 4 つ:

| 場所 | 内容 |
|---|---|
| `td4_config.macro_box()` | `y0 = row_y()[0][MACRO_ALIGN_ROW]` |
| `gen_placement_json` | マクロを `rows[k]` に足し、ピン y を row k 相対に |
| `route_channels_nrow_fm.py` 移植 (3) | `legal=[k]` |
| `place.py` | 擬似行を `k-1` に（横倒しは従来どおり -1） |

`place.py` の `order_rows` も直した。擬似行が実在の行番号になると
マクロが `order` に混ざり、`width['u_mem']` で `KeyError` で落ちていた。

**結果（seed 1、`FILL3` コリドー）:**

| | row0 合わせ | **row1 合わせ** |
|---|---:|---:|
| `CH_HEIGHTS` | `240,230,230,230,210,70` | `250,450,230,190,190,85.4` |
| 高さ | 1403.7 | **1331.2 µm** |
| 短絡 | 4 | 6 |
| DRC | 0 | 0 |
| **clear-x 失敗** | **24**（row0 10 / row1 7 / row2 7） | **6**（row1 2 / row2 4） |
| チャネル残トラック | 37,35,36,36,31,8 | 18,45,40,32,32,9 |

**row0 の行またぎ失敗はゼロになった**（狙いどおり）。ch[0] は 37 → 18 トラックに
減り、代わりに ch[1] が 35 → 45 に増えている。高さも 72 µm 下がった。

**高さの決まり方も変わる。** マクロより**下**のチャネル（ch[0] と ch[1]）は
圧縮が効くので**いくら大きくしてもタダ**。効くのはマクロより上に残る分だけで、

```
コア高 = (ch[0]used + row0 + ch[1]used) + 933 + (マクロ上端より上の圧縮後)
```

3 項目を 0 にするには **ch[2]+ch[3]+ch[4]+ch[5] = 933 + 59.4 − 297 = 695.4 µm**。
`250,450,230,190,190,85.4` はこれをちょうど満たす（230+190+190+85.4 = 695.4）。

**ただし短絡は減らなかった。** 残った警告は全部 **x 1060…1165**、つまり行の
**右端**（マクロ側）に集まっている。マクロの 21 本が行の外（x 1200…1596）から
入ってきて、行の右端で一斉に左へ折れるため。混雑が row0 全体から行の右端へ
移っただけで、量は変わっていない。**これは縦置きの構造そのもの**（マクロが
片側にある）なので、`MEMPORT` のようにピンを幅方向に散らさない限り消えない。

### 帯はルータ座標の「下」に置く

`MEMPORT` は y < 0 に置く。こうするとルータの ch[0] は帯の上から始まり、
トラック割当が帯に食い込まない。パッドはルータから見て負の y にあり、
「row0 のセルのピンが下に飛び出している」ように扱われる（ストラブは
min/max で描かれるので向きは問題にならない）。

帯の上端と y=0 の間は **`MACRO_GAP_UM = 10.8` 空ける**。0 にすると
ch[0] の最初のトラック (y=2.0) と TAP の M2 メッシュ (y=0 から) が
帯の上辺の金属と 1.4/2.0 µm を割る（実測 M1 17 件 / M2 13 件）。

### FILL の詰め方

**右端に固めない。** 区画ごとの目標量を「残りのセル幅 : 残りの容量」の比で
決め（quota）、区画内では `alternate`（偶数区画は右寄せ、奇数区画は左寄せ、
**全行で同じ振り方**）にする。区画の境目に幅の広い空き列が縦一直線に揃い、
行を跨ぐ配線がそこを通る。各行 FILL の塊 3 個 × 約 140 µm。

幅 10.8 の隙間からは via パッド 3.4 + 間隔 2.0 が両側に要るので**行またぎ用の
x が 1 本しか取れない**。140 µm の塊なら 25 本取れる。だから `distributed`
（セル間に散らす）より `alternate` の方が良い。

TAP の左右に置いた優先コリドー（`PRI_MODE="both"`、6 本/行）は区画に含めない。
**グローバル配線用の予約**なので通常の FILL では埋めない。

### 入力は `BUFTH` で受ける

`scripts/insert_bufth.py` が合成の最後（`syn.sh` 6.5）で、トップの入力
9 本（`clk` `rst_n` `exec` `wr` `nibsel` `d[3:0]`）に `BUFTH` を 1 段ずつ挿す。
`OSS_ESD_5V_DIO` に入力バッファが無く、`PAD` の 4.8 pF を外部ドライバが
直接振るため。`BUFTH` はシュミット（立上り 3.71 V / 立下り 1.20 V）。
P&R から見ると 9 セル 291.6 µm が増えるだけで、扱いは普通の標準セル。

## 短絡 3 本を潰す（縦置き・`--balance-tol` 打ち止めの後）

`--balance-tol` も行幅も打ち止めになった時点で残っていた 3 本を、**配置を
いじらずに**潰した。結論から言うと、3 本とも原因が別々で、しかも 1 本は
**ルータの短絡ですらなかった**。

| | 症状 | 本当の原因 | 直し方 |
|---|---|---|---|
| `_063_`↔`wr_hi` | 同じ列で片方が終わる所にもう片方が始まる（重なり 21.6 µm） | 端点の via が**分岐点**（同じネットの別 M2 がそこに乗る）。外すと枝が切れる | 端点を触らない**片側ドッグレッグ** |
| `_069_`↔`ld_addr[2]` | 同上 | 全長 234 µm クリアな列が ±30 トラックに無い | 同上 |
| `reg_out[0]`↔`_050_` | step7 では 0 件、**step8 で発生** | `route_top_pins_nrow_fm.py` が **4 行専用**で、row3 のピンを row1–row2 の帯まで 500 µm 降ろす | ポートの**隣**のチャネルを使う |

### 1. 検出器を step10 と揃える（`component_conflicts`）

`find_conflicts` は net_shapes に記録された箱同士の**正の重なり**しか見ない。
そこから漏れるものが 2 つある:

* 違うネットの箱が**ぴったり接している**（隙間 0）。ルータの
  `_overlapping` 流儀では合法だが、銅では短絡。
* **via のパッド**。via は net_shapes に載らない（PCell が自前で 3.4×3.4 の
  M1/M2 パッドを描く）ので、ネット A の via がネット B の金属に乗っても
  ここからは見えない。

どちらも step10 の `verify_connectivity_nrow_fm_m1m2.py` は見つける。同じ
union-find を **rip-up ループの中で**回すようにした（`TD4_COMPONENT_CHECK=0`
で従来どおり）。効果は実測で出ていて、ドッグレッグの後に残った via 経由の
ブリッジ 2 件を、ループが自分で拾って `try_fix_horizontal` で直している。

### 2. complex ネットの縦箱を安全に動かす

`try_fix_vertical` は complex（多セグメント/高ファンアウト）ネットの縦箱を
一律で拒否していた（RSTB1 事件のカスケード）。その「カスケード」の中身を
はっきりさせると、**端点の via を外すこと**だけだった。そこで

* `vertical_is_simple_span()` — 端点にこの 1 本しか M2 が生えていないか。
  生えていれば via はこのセグメント専用なので外してよい。
* `find_own_trunk(..., near_x=)` — 同じ y に複数の自ネット M1 がある場合、
  **その via に実際に届いている 1 本**だけを採用し、曖昧なら拒否。
* `STRICT_MAX_TRACKS`（既定 30）で移動量を制限し、**優先 M2 コリドーを
  先に試す**。

の 3 条件を付けた `strict=True` を追加した。live チェック（`clear_excluding` /
`via_pad_clear`）は通常経路と共通なので、strict の方が緩くなることはない。

### 3. 片側ドッグレッグ（`try_fix_vertical_detour`）

**これが決め手だった。** 全長を別の列へ移す従来の直し方は
(a) 全長クリアな列と (b) 両端の via を持ち上げる自由、の両方を要求する。
残っていた短絡はその両方が無い:

* `_063_`/`wr_hi` は端点が分岐点、
* `_069_`/`ld_addr[2]` はチャネル 1 本を丸ごと縦断していて、**行の中でしか
  予約されていない**優先コリドーですら全長は空かない。

ドッグレッグはどちらも要らない。両端と via はそのまま、**重なっている所だけ**
横へ逃がす。しかも実測すると重なりは**スパンの端**にあった（片方が終わる所で
もう片方が始まる）ので、曲がる点を端点そのものに置く「片側」版が要る。

```
  _063_  y 818.8..912.6   重なり 891.0..912.6  ← 上端
  wr_hi  y 891.0..1048.8  重なり 891.0..912.6  ← 下端
```

**ドッグレッグが足す via は全部クリアチェックすること。** `(cx, yj)` の分を
落としていて M1 間隔 2 件 + V1 間隔 1 件の DRC を出した（横倒し seed 7 で実測）。

### 4. step8 は 4 行専用だった

`route_top_pins_nrow_fm.py` の中間行の処理は `ch2_lo, ch2_hi = row_y0[1] +
row_h, row_y0[2]` と**固定**で、どの行のポートでも row1–row2 の帯へ落とす。
4 行なら中間行は row1/row2 しかないので正しいが、5 行だと row2/row3 のポートも
そこへ落ちる。実測:

```
[CHECK] out_port[0]  OUTPUT row2  M2 down -> via -> M1 left  (170.1, 1327.8) -> (-0.0, 826.2)
        → x=170.1 を y 824.5..1326.5 まで一直線。同じ列の _050_ (y 837..1076.8) を貫通
```

ポートが乗っている行の**隣**のチャネルを使うようにした
（`band_for()`、`TD4_TOPPIN_ADJACENT_CH=0` で従来どおり）。riser は 1 行分
（約 60 µm）で済み、**14 本すべてが `[OK]`**（`[CHECK]` 0 本）になった。

step8 が描いた形状も net_shapes に記録する（`NET_SHAPES_TP_JSON`）ようにして、
**step8 の後にもう一度 rip-up を掛ける**（step8b、`TD4_RIPUP_AFTER_TOPPINS=0`
で無効）。トップピンのルータには「どのトラックも衝突するので一番マシなものを
選んだ」という無検査フォールバックがあるので、そこの取りこぼしを拾う保険。

### 5. その他

* `TD4_PRL_NETS`（','区切り）で per-row-local を**名指しで追加**できる。
  `ld_addr[2]` は 4 ピン/3 行で `PRL_MIN_PINS`=5 に届かず、兄弟の
  `ld_addr[0]`(6)/`ld_addr[1]`(5) だけが専用トランクを持っていた。ただし
  **入れると ch[3] のトラックが足りずルートが落ちる**（ch[3] は keeping=35 /
  removing=0 で余裕ゼロ）。高さを足せば入るが、ch[2..5] はマクロのスパン内で
  圧縮が効かないので 1:1 で高さに乗る。**今回は使わずに 0 短絡になった。**
* `TD4_PRI_X` で狙い撃ちの追加コリドーを置ける。x=135 に 1 本足して試したが
  **短絡は 3→5 に増えた**（配置が変わって混雑が別の場所へ移るだけ）。
  ピッチを詰めた場合と同じ結論。
* `--balance-tol` は締める側（0.0〜0.03）も全滅（ch[2]/ch[3] のトラック不足で
  ルートが落ちる）。**既定の 0.02 が両側とも最良。**

## step11: マクロ電源の接続（`connect_macro_power.py`）

縦置きでは `REG8x16` が行スタックの右に居て、その**電源ポートは上辺と下辺の
M2 だけ**（LEF の `PIN vdd` / `PIN vss`）。行の電源レールは x ≤ 行幅で終わり、
その右の帯は縦 M2 バスが占めているので、**マクロの vdd も vss も金属では
何にも繋がらない**まま残る。`lvs_pnr.py` がこれを検出していた:

```
** 電源の島が 1 個ある（トップピンに繋がっていない）:
     $3.vdd  端子 1476 本
```

`vss` が GND と同じ網に見えていたのは**基板（bulk）経由**であって金属ではない
（抽出器は NMOS のバックゲートを 1 つのグローバルノードに繋ぐ）。なので
**両レールとも**繋ぐ。

### 通した経路（実測に基づく。座標はハードコードせず導出する）

```
ストラップ帯 y 311.0..333.0（M1 幅 10 µm × 2 本、隙間 2 µm）
  vdd  y 311.0..321.0  x 1145.8..1597.4 / ライザ（M2）x 1594.0..1597.4
  vss  y 323.0..333.0  x 1140.4..1592.0 / ライザ（M2）x 1588.6..1592.0
```

右端 TAP の M2 柱（GND x 1140.4–1143.8 / VDD x 1145.8–1149.2、コア全高を通る）
から、マクロ**右下**の電源ポートへ立ち上げる。

選べた理由:

* マクロの下（x 1198.8–1598.4, y 0–414.4）にはマクロの信号エスケープの
  **横 M1 トランクが 21 本**あるが、**y 209 より下と y 273–334 は M1 が空**。
* **x 1594 の列は y 0–415 が完全に空き**。
* M1 のストラップは信号エスケープの縦 M2 と交差するが**別層なので問題ない**。

### 踏んだ罠

1. **マクロ下辺の長い M1（y 415.5–418.1, x 1198.8 から右）は `vdd`**、
   同じ高さの右端 TAP の M1 レール（x 1139.4–1150.2, y 415.5–420.7）は **`GND`**。
   **同じ高さで別ネットが向かい合っている**ので「行のレールを右へ伸ばす」は
   VDD/GND 短絡になる。この高さは使わない。
2. ライザのクリアランス検査を素直に margin つきで掛けると、
   **繋ぎ先のポートそのもの**を拾って「塞がっている」になる。
   検査は**マクロの下端で打ち切る**（ポートから上はマクロ自身の金属で同じネット）。
3. via_1 の PCell は `x`/`y` を大きくすると**カットを配列にする**
   （3.4 → 1 個 / 6.8 → 4 個 / 10.0 → 9 個）。ただし **`x` は 3.4 のまま**。
   TAP の柱も M2 ポートも幅 3.4 で隣との間隔が 2.0 しかないので、
   横に太らせると隣のネットに当たる。幅は `y` で稼ぐ。

### 置き場所

**step10（圧縮）の後**。前に入れると y が動く/削られる。
`TD4_MACRO_POWER` で on/off（縦置き既定 ON、横倒し既定 OFF）。
`td4_config.FINAL_GDS` が最終 GDS を指す（step11 を回さないときは step10）。

  933 µm のマクロを両端給電にするならチップ組み立てで上からメッシュを落とす。
* 給電点を増やすなら x 1200.0（vss）/ 1275.4（vdd）にもライザを立てられる。

### LVS ソースのファイル名

**`<トップセル名>.spice`**（= `layout/portrait/simulation/td4_soc_arr_nrow_fm.spice`）。
KLayout の LVS は「セル名と同じ名前の .spice」を探す流儀で、`lef/simulation/*.spice`
も `REG8x16.spice` のようにセル名そのもの。`_src` を付けた名前で出したら
ユーザ側でリネームが要った（2026-09-13）。`mklvsnet.py` は `-o` 省略で
`layout/<mode>/simulation/<トップセル名>.spice` に出す。

ユーザ側の KLayout LVS が出す抽出網 `layout/portrait/<トップセル名>.extracted` は
`XM<name> … <MODEL> L=… W=… AS=… PS=…` 形式（`NetlistSpiceWriter` + デバイス委譲）。
**素の `NetlistSpiceReader` で読むとデバイスではなく subckt 呼び出しに見える**
（実測: circuit 94 / device 0）。読み戻して比較するならデリゲートが要る。
`lvs_pnr.py` は GDS から自前で抽出するのでこの問題に触れない。

## チップレベル（`layout/chip/`）

コアが DRC / LVS クリーンになったあと、`OSS_FRAME_GIO`（2500 x 2500、
16 パッド）に落とす。**開口は四隅まで含めて 1840 x 1840**（`frame_opening()`
が frame GDS の図形を実測する。`lef/TR-1um_frame.lef` の OBS は四隅を
360x360 で粗く塞いでいて実在しない崖を作るので読まない）。

コアは 1604.7 x 1357.0、チャネルは上下 241.5 / 左右 117.65 µm。

### 半径の割り当て（`route_chip.py`）

    921.7   パッド端子（P / HIZ / OUT）と VSS の壁ピン
    902.0   VDD リング（幅 10。水平は M1、垂直は M2、四隅に via）
    884.0   GND リング（同上）
    810.0   信号レーン 0、以降 5.4 ピッチ（14 本が 6 レーンに収まった）
    802.35  コアの bbox（x）。y は 678.5

**水平は M1、垂直は M2** を守ると、辺ごとにリングと引き込みの向きが必ず
直交するので、交差は全部 M1 x M2 になる。via を打つのは繋ぎたいところだけ。

### フレームの電源端子は非対称

  * **VDD は M1 が 1 枚だけ** — 上辺中央の (50,920)-(350,934)。
  * **VSS は M2 の幅広**が四辺の壁に散る。下辺中央の (-450,-934)-(50,-920)
    が VSS ボンドパッド P8 の真下。

HIZ は 14 本すべてレール直結で、VDD 側 9 本・GND 側 5 本が四辺に散っている
（+ 入力パッドの浮いた `OUT` 9 本も GND へ）。だからリングを 2 本回して、
端子からは半径方向に一直線で落とす。コア側は上チャネルの M1 バスで VDD
タップ 4 本、下チャネルの M1 バスで GND タップ 4 本を束ね、VDD は M2 ライザ
5 本で上へ（**y=916 で M1 に跳ねる**。M2 のまま 920 まで行くとフレームの
VSS に当たる）、GND は M2 ストリップ 5 本で下辺の VSS 壁ピンへ降ろす。

### 踏んだ穴

* **端子の上に via を打ってはいけない。** フレームの端子 42 本は全部
  M1 + M2 のスタックで、フレーム自身が V1 を打っている（P3 なら M2
  (-923.4,528.3)-(-920,531.7) の裏に M1 (-960,528.3)-(-920,531.7) と
  V1 (-922.4,529.3)-(-921,530.7)）。出ていく向きに合った層を選べば
  重ねるだけで繋がる。左右の辺なら M1、上下なら M2（`edge_layer()`）。
* **足の重なり（`stub_order()`）。** 端子からもコアピンからも配線は辺に
  垂直な「足」でレーンまで出る。同じ辺で M2 なら 5.4 / M1 なら 3.2 µm 以内に
  並んだコア側とパッド側の足は、**パッド側のレーンが外**でないと必ず重なる。
  実際 `cflag_o` のコアピン（上辺 x=-534.1）と `wr` の P2（上辺 x=-530）が
  4.1 µm 違いで、M2 が 0.7 µm まで寄った。`pack()` に下限レーンを渡して解く。
* **接続性の probe は層を指定する。** コアの左辺の M1 ピンは、いちばん左の
  GND TAP 柱（M2、x=-793.35 中心・幅 3.4）とちょうど重なる位置にある。
  層を省いて探ると左辺の 5 本が全部 GND に見える。
* `drc_check_nrow_fm.py` の M2 width はフレーム自身で 2000 件以上出る
  （角のノッチを拾う）。**step1（配置だけ）との差分**を見ること。間隔違反は
  step1 が M2 5 件 / V1 15 件で、どれも |座標| > 920 のフレーム内部。

### REG8x16 の電源（チップ側で受ける）

マクロは vdd/vss とも**上辺と下辺の両方**に M2 ポートを持ち、左右 2 列ある
（LEF: vdd x 76.6-80.0 / 395.2-398.6、vss x 1.0-4.4 / 389.8-393.2、y は
1.1-4.5 と 928.5-931.9 の計 8 本）。マクロの上辺はコアの上辺と面一なので
**上辺のポートはコアの中からは届かない**。step11 の `connect_macro_power`
が右下の 1 組だけ行の電源に繋いでいるのはそのため。

チップ側には上下のチャネルに M1 のバーがあるので、`route_chip.py` が
そこまで M2 をまっすぐ延ばす:

    vdd 上辺 2 本 -> 上の VDD バー（y 678.5 -> 690、12 µm）
    vss 下辺 2 本 -> 下の GND バー（y -250.0 -> -690、440 µm）

下側は**行の右側の空き**（行幅 1150.2 に対しマクロ左端 1198.8）を通る。
この 2 列は M2 も V1 も空で、横切るのは別ネットの M1 だけ（左列 23 本 /
右列は step11 のストラップ）。M2 x M1 なので via を打たなければ何も起きない。
バーの x 範囲はライザを含むように右へ伸ばす（VDD は 807.6、GND は 802.2 まで）。

結果、左右どちらの柱も両端から給電される。`verify_chip.py` が 8 本すべて
レールの島に入っていることを確認する。

### `TD4_MACRO_MODE` を付け忘れると step10 を載せる

`TD4_MACRO_MODE` の既定は **landscape**。付け忘れると

  * `FINAL_GDS` が step10（マクロ電源**なし**）を指す
  * `MACRO_CELL` が REG8x16 ではなく MEMPORT になる

2026-09-14、これでマクロ電源の入っていないコアを載せたチップを組んでいた
（DRC も接続性検査も通る。マクロの vdd/vss は基板経由でしか繋がっていない）。
チップ側のスクリプトは先頭で `os.environ.setdefault("TD4_MACRO_MODE",
"portrait")` して固定してある。加えて `td4_config.CHIP_CORE_GDS` は
step11 があればそちらを選ぶ。

### step4: OpenSUSI ロゴ（`place_logo.py`）

`lef/opensusi_logo.txt`（5 µm 格子のビットマップ、317 x 63）から**紋章だけ**
（0〜64 列）を切り出して 2:1 に縮約し、**3.0 µm 角の M2 ドット 646 個**を
5.0 µm 格子で置く。塗りつぶしではなくドットにするのは、

    ドット 3.0 µm      = M2 の最小幅ちょうど
    上下左右の隣        = 5.0 - 3.0 = 2.0 µm = M2 の最小間隔ちょうど
    斜めの隣            = 2.83 µm

で、どちらの検査も「未満」を違反とするから。移植元（I2C）は 5 µm の塗り
つぶしで描いて斜めの角が触れ、手で直している。

置き場所はチップ全体で**いちばん広い空き**を実測で求めた
**(410, -680)-(790, -470) の 380 x 210 µm**（マクロ REG8x16 の下、行の右側、
GND ライザ 2 本の間）。ロゴ全体（1,583 x 313 µm）は入らない。文字まで入れると
5:1 まで縮めることになり、その縮尺では字が潰れて読めない。

ロゴ単体で DRC を掛けてから置き、置いたあとにチップ全体を見て**新しい違反が
0 件**であることを確認する。LVS は浮いたドットを `purge_nets()` が落とすので
一致のまま。
